# SRS-301.4 — Extraction request (AO)

> **SRS-301.4, AO, Extraction request.** The system shall create one extraction request linked to the signed-in user when the user confirms extraction of the selected document.
>
> **Acceptance:** Given document X is selected, When the user confirms extraction, Then exactly one extraction request for document X exists and it is linked to the user's account.

## What was built

| File | What it does |
|---|---|
| `app/extract/page.tsx` | Extraction page: pick a document, see its title, confirm, see the new request in "My extraction requests" |
| `app/api/extractions/route.ts` | `POST` creates one `Queued` extraction for the signed-in user · `GET` lists only that user's extractions |
| `app/api/extractions/documents/route.ts` | `GET` lists documents to choose from |
| `lib/extractions.ts` | Shared types and the exact SRS messages |
| `supabase/seed_extraction_demo.sql` | Demo data: Salem, City Council, one meeting, 2 PDFs + 1 Word file |
| `__tests__/api/extractions.test.ts` | 12 tests covering the acceptance criteria |

Also covered on the way, because each was a few lines: **SRS-301.1–301.3** (select, show title, button disabled with nothing selected), **SRS-301.5/301.6** (non-PDF rejected with the exact SRS message), and **SRS-306.3** (no duplicate request while one is still Queued/Processing).

## Setup (one time)

1. `.env.local` filled in as in the README (the service-role key is required).
2. Supabase SQL Editor: run `supabase/schema.sql`, then `supabase/seed_extraction_demo.sql`.
3. `npm install`, `npm test`, `npm run dev`.

## Demo script

1. **Register** a user at `/register`, then **log in** at `/login`.
2. Go to `/extract` (or use "Request contact extraction" on the home page).
3. Show the **Request extraction** button is disabled — nothing selected yet *(SRS-301.3)*.
4. Click **City Council Regular Meeting - Agenda** → it's marked **Selected** and its title appears under "Selected document" *(301.1, 301.2)*.
5. Click **Request extraction** → **Confirm extraction**.
6. The request appears under "My extraction requests" with status **Queued** *(301.4)*.
7. Prove it in the database (Supabase SQL Editor):
   ```sql
   select e.extraction_id, e.document_id, e.status, u.email
   from extractions e join user_accounts u using (user_id)
   order by e.extraction_id desc;
   ```
   Exactly one row for that document, linked to the logged-in user's email.
8. *Bonus:* select the agenda again — the button stays disabled, "already in progress" *(306.3)*.
9. *Bonus:* select **Public Comment Notes** (a Word file) and confirm → "This file can't be extracted. Only PDF documents are supported." and no row is created *(301.5, 301.6)*.

## Notes for the team

- `extractions.user_id` references `user_accounts`, but the starter's register route only creates the Supabase auth user. The POST route creates the `user_accounts` row if it's missing. Whoever owns accounts (KJ) may want to move that into register.
- The extraction itself (reading the PDF, finding officials) is not part of 301.4. Requests stay `Queued` until that worker exists (UR-302 / UR-306).
